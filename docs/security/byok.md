# Self-managed provider connections

InView requires each reader's own OpenAI, Google, Typesafe, Exa and Monid keys. There is no fallback to the application's environment keys. Existing X OAuth and account-bound Postiz publishing are separate integrations.

## Trust boundary

This is encrypted server custody, **not zero knowledge**. The browser necessarily holds a key while its owner enters/submits it over HTTPS. Next receives it, encrypts it, and the execution adapter decrypts it briefly to authenticate to the selected provider. The server operator or an attacker controlling application execution could obtain keys. Encryption protects a database-only disclosure; it does not protect a compromised runtime. JavaScript cannot guarantee erasure of all memory copies. Do not promise otherwise in product/privacy copy.

Keys live only in `provider_connections` as AES-256-GCM ciphertext with a fresh 96-bit nonce and 128-bit tag. Authenticated data binds the deployment context, owner, provider, connection UUID, encryption key ID and expiration. Replacements receive a fresh UUID. No plaintext compatibility mode, partial key display, plaintext cache, list/reveal/export endpoint, browser storage or key-bearing model/tool argument exists. Successful upstream response streams filter exact reflected credentials across chunk boundaries; upstream error bodies and arbitrary headers are discarded. This is defense in depth, not a claim that arbitrary third-party encodings can be detected.

A separate `server-only` module reads a versioned keyring from protected runtime configuration, never from the database. The server-only marker is enforced in Next builds; trusted standalone workers use Node's `react-server` condition. Node tests use a test-only marker adapter because they also render client React components.

Management requires a Clerk session, matching account header, exact same origin and bounded JSON. Agent bearer tokens cannot manage credentials. Mutations are limited to 20 per owner per minute using PostgreSQL. Responses are private/no-store and contain metadata only. The form clears the password on submission (also on failure) and unmount; account switches remount the form. Do not add session replay or request-body logging to this screen/endpoint.

Execution uses a metadata-only connection ticket. Immediately before sending, an owner-locked database function authorizes the same owner/provider/UUID and records metadata only. Save, disconnect, rotation, deletion and authorization acquire the owner lock before credential row locks. The adapter rechecks expiration after the database response and decrypts. The operation selects an immutable HTTPS URL/auth-header mapping; caller URLs and redirects are forbidden. Disconnecting/replacing blocks subsequent dispatch authorizations using an old ticket. Requests already authorized may still reach the provider or finish, including when the authorization response is delayed in transit. The database transaction and external provider send cannot be atomic; this boundary is explicit in the UI and race tests. Failures known to precede dispatch release their paid reservations; ambiguous network outcomes remain reserved and require existing reconciliation.

PostgreSQL atomically enforces a reader's cumulative cap (default $10, editable $0–$1,000) and at most 16 unresolved/in-flight reservations, matching the existing classification capacity. Disconnection does not reset spending. Existing per-model bounds, duplicate-operation guards, uncertain-charge reconciliation remain active. New BYOK reservations use independent user budgets; historical attempts and the deployment budget retain their original accounting and reconciliation. Historical usage cannot consume a new BYOK allowance, but the same unresolved operation cannot be replayed across the cutover. The app's accounting does not cover use of the same key elsewhere, provider price changes or provider-side billing errors. Users should set provider-side limits and use dedicated, minimally scoped keys.

## Production activation

1. Apply the normal recorded migrations, including `026-provider-connections.sql`, against the intended database after the usual backup/restore check. Tests run against isolated PostgreSQL; they do not migrate Neon.
2. Generate a random 32-byte master key using a cryptographic generator. Save it to a protected local file or directly into the existing hosting secret configuration; do not paste it into chat, logs, tickets or source control. Set `PROVIDER_CREDENTIAL_KEYS` to a JSON object mapping IDs to canonical base64 keys, `PROVIDER_CREDENTIAL_ACTIVE_KEY` to the write ID, and `PROVIDER_CREDENTIAL_CONTEXT` to a unique stable environment identifier. Example shape only: `{"v1":"<base64-32-random-bytes>"}`. Development, preview and production require separate keys, contexts and databases. Never grant an untrusted preview production database/key access.
3. Keep the keyring and backups under access controls separate from database access. Limit who can read deployment secrets, change production code or access runtime diagnostics. Never use `NEXT_PUBLIC_` variables for encryption material. Preserve recoverable keyring backups separately; losing the keyring makes stored keys unusable. Missing/invalid keys fail closed.
4. Subscribe the existing Clerk instance to `user.deleted` at `/api/webhooks/clerk` and set `CLERK_WEBHOOK_SIGNING_SECRET`. The endpoint verifies the signed raw body with Clerk's SDK, bounds the body, retries failures via a non-2xx response, and is idempotent. Test a disposable account deletion through the real Clerk instance before launch. Deletion removes active ciphertext and management metadata and retains a minimal owner tombstone to reject delayed saves. The existing paid ledger remains for reconciliation; broader account-data deletion is outside this credential feature.
5. Enable the existing authenticated daily processing cron (`CRON_SECRET`) so expired ciphertext and audit metadata are pruned. Expired keys are unusable immediately even if the cron is delayed. Monitor webhook failures and cron execution. A standalone operator can run `npm run credentials:maintain -- prune` against the explicitly selected environment.
6. Require HTTPS. Disable credential-route body/header capture, SQL parameter capture, session replay, error payload capture and heap dumps in production tooling; verify existing hosting/observability configuration rather than assuming code can control external capture. Audit rows contain only owner/provider/action (including authorization)/time, retained for 30 days. Database backups/PITR can retain old ciphertext after disconnect, expiration or deletion: configure and disclose the actual retention window, restrict restores, and reapply deletion events/tombstones before restoring service. Do not claim immediate deletion from backups.
7. Verify save/use/replace/disconnect, two-account isolation, expiration, keyring failure and signed deletion in the deployed staging environment using disposable restricted provider keys. Local tests mock external providers and do not prove real provider access, hosted TLS/logging, Clerk delivery or deployment-secret configuration. Remove any obsolete shared AI/research keys from application deployment configuration when no operator-only evaluation scripts need them.

## Rotation and incident response

Add a new random key under a new ID while retaining the old keys, set the active ID, and deploy the keyring consistently to all app/worker instances. Run `npm run credentials:maintain -- rotate` using protected runtime configuration. This processes bounded pages and compare-and-swap updates; it never exports plaintext. Concurrent replacement/disconnection wins over a stale rotation update. A failure stops rotation; keep all needed keys and rerun after repair. Confirm no live rows use retired key IDs and all instances have the new configuration before removing old keys. Old backups need an appropriate separately controlled recovery keyring until their retention expires. Changing the context is not a rotation mechanism.

For a suspected runtime/master-key compromise: pause paid dispatch, revoke affected provider keys, rotate the deployment keyring and credentials, investigate access/code changes, and follow the applicable incident-response obligations. Re-encrypting with a new master key cannot revoke API keys already stolen. For suspected database-only disclosure: assess master-key exposure independently and rotate as warranted. Never include decrypted credentials in an incident report.

## Inspected open-source references

These are design references, not imported code or claims of equivalent security:

- [n8n encryption cipher, pinned 3b2addb](https://github.com/n8n-io/n8n/blob/3b2addb585b27518971a3f44b11cc6f4334b3c79/packages/core/src/encryption/cipher.ts): key IDs and active-key rotation; InView does not adopt legacy CBC or compatibility behavior.
- [LiteLLM encryption helpers, pinned 6a1f81b](https://github.com/BerriAI/litellm/blob/6a1f81b9f8bd365718e781c50141fd3164721dbb/litellm/proxy/common_utils/encrypt_decrypt_utils.py): versioned authenticated encryption and associated data; InView requires authenticated encryption and rejects plaintext fallback.
- [LiteLLM per-user credentials, same pin](https://github.com/BerriAI/litellm/blob/6a1f81b9f8bd365718e781c50141fd3164721dbb/litellm/proxy/credential_endpoints/user_provider_credentials.py): owner-scoped encrypted credentials. InView does not cache credentials, so disconnect takes effect at the next serialized dispatch authorization.
